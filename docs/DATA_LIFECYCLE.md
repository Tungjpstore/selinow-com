# Data lifecycle

Phase 9 uses resumable D1 workflows for seller exports and shop deletion. Orders, payments, audit logs, abuse evidence, and moderation records are retained; the deletion API never performs a shop-wide `DELETE CASCADE`.

## Seller exports

- `GET /api/app/shops/{shopPublicId}/exports` lists the owner's recent jobs.
- `POST /api/app/shops/{shopPublicId}/exports` creates either a `standard` export or the separate high-risk `inventory_keys_plaintext` export. The latter requires `acknowledgePlaintextRisk: true`.
- `POST /api/app/shops/{shopPublicId}/exports/{exportId}/download` consumes a short-lived one-time token and returns the JSON attachment.
- Standard exports select inventory metadata only. They never select or decrypt inventory ciphertext.
- Standard export schema version 5 includes safe manual-fulfillment, generic-entitlement, payment-reversal and generated-license lifecycle metadata. Generated-license projections include only connection/binding/snapshot/request/attempt/artifact/DLQ identifiers, statuses, versions, safe error codes and timestamps. They exclude endpoint and credential values, ciphertext, IVs, key versions, fingerprints/hashes, provider references and artifact plaintext. The reversal projection remains limited to public order/attempt references, provider, reversal kind, decision, verification method, amount/currency, reason and timestamps. Buyer/replay/reference hashes, manual/reversal/generated-license idempotency/request/evidence/reference hashes, grant request IDs, credential/integration IDs and every external-reference plaintext value are omitted.
- Export JSON is AES-GCM encrypted with versioned AAD before upload to the private `PRIVATE_EXPORTS` R2 bucket. Download verifies integrity and decrypts before atomically consuming the token.
- Scheduled retention maintenance processes a bounded batch of rows whose `retain_until` has passed. It revokes any unconsumed token before deleting only the canonical `exports/{exportId}.bin` object, records a safe retry code on R2 failure, and never follows a tenant-supplied object key outside that exact shape.

All export mutations require an owner session, recent authentication, JSON content type, and CSRF. Required configuration is `PRIVATE_EXPORTS`, `EXPORT_KEK_V1`, and `EXPORT_KEY_VERSION=v1`.

## Protected backup and restore

Protected D1 backups include the authoritative subscription, plan/price, billing account, checkout, invoice, provider-event, subscription-event, usage counter/event and `activation_milestones` tables. Restore drills require those tables in the isolated target and compare their per-table row counts with the source before the target is accepted. The drill also runs SQLite integrity and foreign-key checks. Missing tables, missing rows, orphan rows, or a cross-tenant billing reference fail closed; provider subscription events must point to the same tenant as their explicit provider event, invoices must use a billing account owned by the invoice tenant, and `trial_converted` milestones require provider-backed activation evidence. Raw provider payloads and credentials are never included in backup reports.

## Shop deletion

- `POST /api/app/shops/{shopPublicId}/deletion` requires `confirmation: "DELETE SHOP"`, immediately suspends checkout, and removes active storefront routing.
- `GET /api/app/shops/{shopPublicId}/deletion` returns the request and step checkpoints.
- `POST /api/app/shops/{shopPublicId}/deletion/resume` retries blocked or failed steps.
- `POST /api/app/shops/{shopPublicId}/deletion/cancel` lets the shop owner cancel the exact tenant-owned request while no lease is active and no irreversible step has started. The request must include its deletion request ID and current expected version.
- `POST /api/admin/operations/deletions/{deletionRequestId}/legal-hold` lets a platform `owner` or `risk` operator set or release a bounded legal hold for the exact shop/request pair with the current expected version, a safe reason/evidence reference and a unique idempotency key.

All deletion mutations require recent authentication, JSON content type, CSRF and tenant/admin authorization. Cancellation and legal-hold changes use optimistic version checks and fail closed on stale state, active leases or invalid scope. Cancellation restores the pre-deletion shop/subscription/routing state recorded by the request; it cannot reverse a provider cleanup or crypto-shred step.

The active workflow waits for active or exceptional payments, a 30-day export grace period, any legal hold and every active work lease. It then removes provider resources with leased checkpoints, revokes integrations, cancels and revokes tenant export jobs, deletes their exact private objects, crypto-shreds inventory and credential ciphertext, archives the shop, and cancels its subscription. A live generated-license processing lease blocks the destructive step with `shop_deletion_generated_license_work_inflight`. The export-object fence is completed before `secretMaterialDestroyedAt` is written; legal holds and provider/object failures keep that marker unset so the step can retry. Financial records remain retained for seven years by metadata and are not physically deleted in Phase 9. This retained evidence includes immutable `manual_fulfillment_executions` and hash-only `external_fulfillment_references`; deletion does not update or delete those ledgers, and there is no recoverable reference plaintext to shred.

Migration `0047_generic_entitlement_foundation.sql` adds lifecycle handling for `entitlement_resources`, `product_entitlement_policies`, `order_item_entitlement_requirements`, `entitlements`, `entitlement_grants` and `entitlement_transitions`. Standard exports expose the safe resource/policy/requirement/state/grant/transition projection but exclude buyer binding hashes, grant request IDs and other replay material. During admitted deletion, the existing legal-hold and crypto-shred fence retires active resources and policies, revokes pending/active/suspended entitlements and appends immutable `shop_deleted` transitions. Requirements, grants and transitions remain retained evidence and are never rewritten or physically deleted by the workflow. The schema is present in the admitted production baseline through `0052`; no staging continuation or provider-backed lifecycle activation has been executed.

Migration `0048_payment_reversal_entitlement_revocation.sql` adds the immutable `payment_reversal_events` financial/audit ledger. The current standard export schema v5 safe projection never includes provider-reference, evidence, idempotency or request hashes, raw references, credentials or integration identifiers. Protected backup schema/count validation includes the reversal ledger and fails an isolated restore on any missing row. Shop deletion does not update or delete reversal events, sold inventory keys, fulfillment rows, entitlement grants or delivery-consumption history. A non-exact reversal creates an open `manual_review` payment exception, so the existing active-payment admission check blocks destructive deletion until the exception is resolved.

Migrations `0049_generated_license_fulfillment.sql` and `0050_generated_license_deletion_lifecycle.sql` add the generated-license lifecycle. D1 owns the provider configuration, immutable requirement snapshot, request/retry/reconciliation state, immutable attempt evidence, encrypted artifact status and generated-license DLQ/operator state. The queue and DLQ remain reference-only. Free checkout creates a generated request only after the active entitlement and `free_checkout` grant exist; paid checkout creates one only after the exact signed/claimed unprocessed `paid_exact` event activates the entitlement. Website, Telegram and `fake.third` use the same lifecycle boundary.

An exact verified reversal is local-only: pending, retryable, reconcile-pending and processing requests are canceled, active artifacts are revoked, and no provider call is made. Immutable requests and attempts remain retained. During admitted shop deletion, non-terminal requests are canceled, open DLQ rows are resolved with the safe deletion code, active bindings and connections are retired, credential and artifact envelopes are crypto-shredded, and immutable requirement/request/attempt evidence remains. Migration `0051_generated_license_rotation.sql` keeps credential and artifact re-encryption separate and resumable: `generated_license_credentials` uses the credential key family, while `generated_license_artifacts` uses the inventory key family. Migration `0052_generated_license_request_hardening.sql` freezes canonical request creation, terminal evidence and retry/lease transitions and adds the global scheduler/key-version indexes. Scheduled expiry marks due generic entitlements expired; Website and Telegram buyer reveal recheck active paid access and `access_expires_at` before decrypting an artifact. Backup/restore schema and authoritative row-count validation cover all eight generated-license tables. The schema is included in the admitted production baseline through `0052`; staging remains at 28 applied migrations with 41 source migrations (`0029`-`0069`) pending, and provider-backed execution remains `NO-GO`.
